# Handy review

## 1) Scope and verdict
Handy at pinned SHA `4006c92465b0c90406b4bc2aa6f21c92b3b47806` is an implementation-stage robot-operator prototype centered on `so101-domain-operator`, not a production-validated hardware system. Runtime was **not run**. This review uses only inspected numbered-source ranges [S1]-[S11] plus the local snapshot inventory for naming uninspected boundaries. The inspected slice confirms several **simulator/source-level safeguards**—checksum rejection, torque-off initialization, failed-grasp aborts, dry-run non-actuation, and a repair mission that does not enable torque itself—but it does **not** prove the live UI→API→bridge→serial authority path, operator authorization, emergency-stop reachability, or physical recovery because `src/app/api/*`, `src/lib/arm.ts`, `src/lib/missions.ts`, `src/lib/persist.ts`, and `public/bridge/so101_bridge.py` were not inspected.

## 2) Architecture and product boundary
The real product boundary is broader than the root README. `package.json` shows a Next.js operator app with `dev/build/start`, default `test`, opt-in `test:live`, a bundled `so101` Node tool, and Python YOLO helpers [S1]. The bridge environment is separate again: `requirements.txt` gives only `websockets>=12`, `pyserial>=3.5`, plus a comment to install `lerobot[feetech]` [S2]. `scenarios/index.ts` embeds a LeRobot sample that connects on `/dev/ttyACM0` and calls `robot.send_action(...)`, so this is a hardware-control surface, not just a web app [S4]. State ownership is explicit too: `db/index.ts` says Postgres is only a backup and `localStorage` is the source of truth [S5]. Testing is split between a default Node/Vitest gate [S3] and an opt-in virtual-arm suite that says “The default `npm test` skips it” [S6].

## 3) Findings ledger
- **H-01 — Medium, confirmed static, high confidence. Default continuous verification excludes the strongest end-to-end mission coverage.** `vitest.config.ts:4-6` includes only `"src/**/*.test.ts"` in Node [S3], and `all-missions-live.test.ts:7-11` says the virtual-arm suite is opt-in and “The default `npm test` skips it” [S6]. Impact: the repository contains useful simulated end-to-end coverage, but default execution does not continuously re-prove reachability and no-crash behavior across every shipped mission. Recommended correction: keep the virtual-arm suite, rename its proof boundary clearly, and add a separate acceptance gate for supervised live hardware rather than letting `test:live` imply bench proof.

- **H-02 — Medium, confirmed static, high confidence. The supported bridge/runtime matrix is under-specified across both JavaScript and Python.** `package.json:17-40` pins `next`, `react`, `pg`, and `typescript`, but leaves `serialport` at `^12.0.0` and `vitest` at `^3.2.7`, and no `engines` field is declared anywhere in the inspected range [S1]. `requirements.txt:1-3` is looser still: `websockets>=12`, `pyserial>=3.5`, plus a comment-only `pip install 'lerobot[feetech]'` instruction [S2]. Impact: the bridge can drift under routine install activity even when application code has not changed, making it hard to tie observed robot behavior to a known Node/Python/LeRobot stack. Recommended correction: publish one tested compatibility matrix covering Node, Python, LeRobot, `serialport`, `websockets`, and `pyserial`, then make future release notes refer back to that matrix.

- **H-03 — High, unverified risk, medium confidence. Safety evidence exists, but it is mostly simulator/source-level and does not yet prove the live actuation boundary.** The inspected tests do show real safeguards: `driver.test.ts:14-19` “rejects bad checksums” [S7]; `review.test.ts:50-61` says initialization “ends torque-off” and leaves goals at present position [S8]; `review.test.ts:128-143` ensures missions stop “after repeated failed grasps instead of looping forever” [S9]; `repair.test.ts:117-136` proves “dry-run writes nothing to the servos” [S10]; and `repair.test.ts:210-216` asserts “the mission never enables torque itself” [S11]. But `scenarios/index.ts:32-41` also publishes a direct control example that does `robot.connect()` and `robot.send_action(...)` to `/dev/ttyACM0` [S4]. Impact: the inspected slice supports a careful statement—there are simulator-side and source-level controls—but it does not support claiming that the shipped runtime path enforces operator authorization, stale-command rejection, emergency-stop access, or safe reconnect behavior on real hardware. Recommended correction: trace the uninspected UI/API/bridge/serial path, document the exact actuation authority boundary, and require independent supervised bench acceptance for anything beyond simulation.

- **H-04 — Medium, confirmed static, high confidence. State authority and recovery semantics are documented only halfway.** `db/index.ts:4-23` says `localStorage` is the source of truth, Postgres is “only a *backup*,” `next build` must work without a database, and `getPool()` throws if `DATABASE_URL` is absent [S5]. Impact: the code comment establishes a philosophy but not a recoverable policy: the inspected slice does not say when backup writes occur, how divergent local and Postgres state is reconciled, or what restore success looks like after a partial failure. Recommended correction: define backup timing, conflict resolution, restore ownership, and failure signaling before treating the backup path as operational protection.

## 4) Five-discipline assessment
**Code/correctness.** The tests verify protocol parsing, torque-off initialization, idempotent connect-time setup, failed-grasp aborts, dry-run non-actuation, and closed-set repair verdicts [S7]-[S11]. The main correctness unknown is the uninspected runtime path.

**Automation/testing.** The negative tests are meaningful, not tautological, but default `npm test` does not cover the stronger virtual-arm suite and no inspected source ties hardware acceptance to an independent gate [S3], [S6].

**DevOps/operations.** The scripts imply a multi-runtime surface—Next.js, bundled Node tooling, Python helpers, optional Postgres, serial bridge [S1]-[S2]—but restart, restore, and serial ownership recovery are unproven in the inspected slice.

**OWASP/security.** No inspected source demonstrates authn/authz, origin checks, or command authorization on the UI→API→bridge path. Those controls may exist, but not in the reviewed slice [S4].

**UI/UX/accessibility.** No UI files were inspected, so emergency-stop prominence, sim-vs-live labeling, and disconnect signaling cannot be scored directly. The architecture still makes those states safety-critical [S5], [S6], [S10]-[S11].

## 5) Production blockers and owner questions
1. Which exact runtime file/range enforces command authorization, stale-command rejection, and disconnect recovery?
2. What is the approved support matrix for Node, Python, LeRobot, `serialport`, `websockets`, and `pyserial`?
3. When `localStorage` and Postgres disagree, which copy wins and what proves restore success?
4. What is the deployment/restart order for the Next app, Python bridge, and serial device?
5. What independent artifact is required before any physical-readiness claim?
